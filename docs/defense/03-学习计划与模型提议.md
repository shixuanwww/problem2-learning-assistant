# 03 · 学习计划与模型提议（`plan.ts`）

## ① 这段代码干什么

两件事：
1. **给每个知识点填"学习动作"**（`fillActions`）—— `makePlan` 只负责排知识点的顺序，
   "这个知识点该怎么学（先读哪份资料、要不要讲解、做哪道题）"在 `plan.ts`。
2. **模型提议通道**（`proposePlan`）—— 让模型可以"提一个学习计划草稿"，但**必须通过校验才会被执行**，
   不通过就**拒绝 + 记日志 + 回落到规则版计划**。

## ② 关键设计决策 + 为什么

### 2.1 学习动作的填充规则（§4.7）

| 规则 | 为什么 |
|---|---|
| **前置点未掌握 → 在本点动作序列最前补一个"前置点资料 Read"（拿不到资料就补 Explain）** | 直接做本点的题会卡在前置上。**注意只改本点的动作，不改知识点顺序** —— 知识点顺序由拓扑序决定，动作是"学这个点之前先垫一下"。 |
| **🔴 同一份资料只读一次（去重）** | 前置点与本点常常在**同一份教材**里，规则 4 的 Read 和规则 1 的 Read 会指向同一个文件 ⇒ 修前计划里出现 `[读 X, 读 X, 讲解, 做…]`，演示时一看就像 bug。现在统一走 `pushRead`（去重键 = 归一化资源路径）。 |
| **未掌握 → `读资料 → 讲解 → 做真题`** | 对应题面示例里的"先讲知识点 → 再做练习"。读资料在前，是因为有了出处才讲得准。 |
| **🔴 选"主"真题先看题型是否薄弱（`kindState < 0.8`），再看考频** | 题面 L3 完成标志③要的是"增加**薄弱题型**训练"。修前 `kindState` **只被写、不被读** ⇒ 题型掌握度对计划零影响，这条标志等于没落实（用例 28 钉住）。 |
| **未掌握 → 再把**回炉题**各追加一道（动作数增加）** | 这是题面第 5 步要看的"可观测变化"。回炉题的定义在 §2.2；回炉题之间也**薄弱题型优先**。 |
| **已掌握（≥ 0.8）→ 只留一道巩固题，不补 Read/Explain** | 已经会了就别再占学习主线，留一道防止遗忘即可。 |
| **🔴 排序键第一项必须是"未掌握在前"（`已掌握 ? 0 : 1`）** | 这是 `makePlan` 里 `compareByPlanKey` 的事（`network.ts`）。修前写成 `已掌握 ? 1 : 0` 再升序 ⇒ **已掌握的点排到最前**，与题面"降低已掌握内容优先级"正好相反（用例 30 钉住）。 |

### 2.2 "回炉题"的依据：只读结构化数据，不解析人类可读文本

`reviewProblemNames()` 的做法是：

```
从 data/answers.json 里筛：pointNames 含该点 且 status !== "correct"  →  取 problemName
```

🔴 **为什么不用 `history.json` 的 `detail` 文本？**
> `detail` 是给人看的自然语言（`"做真题「2023 期末 第1题」→ incorrect（题型 计算）"`）。
> 去**解析**这段文本判断对错，等于把"人读的东西"当"数据"用 —— 格式一改就全错。
> 所以我在记录时**同时**存一份结构化的 `AnswerRecord[]`（题名 / 题型 / 状态 / 涉及知识点），
> 回炉题、题型掌握度、上下文包全从这里取。

### 2.3 模型提议的校验（§4.13）

模型只能返回"知识点名 + 动作意图"的 JSON 草稿，**不得直接改 state**。校验必须**全过**：

| # | 校验 | 不过的后果 |
|---|---|---|
| 1 | schema 校验（字段 / 类型 / 枚举） | 拒绝 |
| 2 | 每个知识点名按归一化名能在图里查到（`dead` 点不算） | 拒绝 |
| 3 | `Read` 的 resource **必须在该点的 `resources` 里** | 拒绝 |
| 4 | `Do` 的 `problemName` **必须已在 `problems` 里** —— **禁止模型编造真题** | 拒绝 |
| 5 | 顺序必须满足 `from → to` 拓扑约束 | 拒绝 |
| 6 | **每个存活知识点恰好一次**（不重复、**也不遗漏**） | 拒绝 |

**拒绝之后做什么**：① **不执行**；② 记一条**决策日志**（拒绝理由 + **原始草稿**）到 `data/decisions.json`；
③ 交回调用方**回落**到 §2.1 的规则版计划。演示脚本里会把这整条链路打印出来。

| 决策 | 为什么 |
|---|---|
| **模型只能提"知识点名 + 动作"，不能提"新知识点"** | 一旦允许它提新点，幻觉进来的点就变成了体系的一部分，不可逆。 |
| **拒绝时记"原始草稿"** | 便于事后回答"模型当时到底提了什么" —— 这是"可回放"的最低要求。 |
| **`accepted=false` 时仍然返回 `plan: undefined` 而不是"尽力执行一半"** | 半执行的计划更容易出问题（比如只排了 1 个点，剩下全漏）。**要不就全过，要不就全拒**。 |
| **校验 6（恰好一次）是后补的** | 早期只查了"不重复"，**没查"不遗漏"** ⇒ 一份只提议 1 个点的草稿也会被接受，
  和规则版计划"必须覆盖全部点"的口径不一致。现在两条路径口径统一。 |

## ③ 可能被追问的问题

**Q：模型提议这条通道是"真的接了模型"吗？**
> 通道**是真的**（`proposePlan` 就是一个公开函数，输入是模型的 JSON 输出，输出是接受/拒绝）。
> 演示里我是**手工构造草稿**喂给它看校验行为 —— 因为我要演示的是"非法提议被拒"这条**确定性**路径，
> 用真模型跑反而不稳定（它可能刚好猜对）。这点我不含糊：**校验逻辑是实测过的，模型调用是接在同一条通道上的。**

**Q：为什么"回炉题"要排除在"主题"之外？**
> 否则"主题"可能刚好就是回炉题，那做错之后动作数**不会增加**（只是同一道题出现在同一位置），
> 第 5 步的"计划因表现而调整"就看不出来了。分开放，答错后动作数一定 +1。

**Q：已掌握的点为什么只留一道巩固题？**
> 因为计划是**有序的**，已掌握的点排在后面（排序键第一项就是"是否已掌握"）。
> 它不占学习主线，但完全不出现又不好（会忘），所以留一道。

**Q：`proposePlan` 接受后返回的 `plan`，和 `makePlan()` 的结果一样吗？**
> 不一定。`proposePlan` 接受的是**模型给的顺序和动作**（只保证满足拓扑序和覆盖完整）；
> `makePlan()` 是**规则版**（按掌握度 + 考频的排序键）。
> 两者都合法，但来源不同 —— 前者是"模型提议"，后者是"规则兜底"。

**Q：如果模型的提议合法但很烂（比如把简单的点排最后），你会执行吗？**
> 会。因为"合理"没有客观判据，而"合法"有（拓扑序 + 覆盖完整 + 引用真实资源）。
> 我选择**只做可判定的校验**，不做主观打分 —— 这也是"能讲清"的一部分：**我能说清我拒了什么、为什么拒**。

**Q：决策日志存在哪？重启还在吗？**
> `data/decisions.json`，与 `answers` / `history` 同策略：**原子写 + 保留最近 500 条**，重启后载入。

⚠️ **Q：题型掌握度（`kindState`）到底参与了哪些决策？**
> 三处：① **选主练习题**优先挑薄弱题型（`kindState < 0.8`）；② **回炉题**之间也按薄弱题型排序；
> ③ **喂给模型的上下文包**里带上相关题型的掌握度（让它调整讲解详略）。
> ⚠️ 这是 2026-10-11 审核**补上**的：修前 `kindState` 只被 `record()` 写、没有任何读的地方，
> 也就是说"题型掌握度"当时是个**只存不用的数字** —— 题面 L3 完成标志③的"增加薄弱题型训练"没落实。

⚠️ **Q：演示里"连续答对到跨过阈值"这一段，为什么要连做 5 次？**
> 因为本题的掌握度公式是定值增量：`correct +0.15`、`incorrect −0.25`、阈值 `0.8`。
> 从做错后的 `0.25` 起步，要 4 次才过 0.8（`0.40/0.55/0.70/0.85/1.00`，我打了 5 次留余量）。
> 这一段就是为了让"**已掌握的点被排到最后**、动作收敛成一道巩固题"这两件事**可观测** ——
> 只做一次对（0.40）是跨不过阈值的，排序键第一项根本没变，演示会看不出变化。
