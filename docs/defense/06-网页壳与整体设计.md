# 06 · 网页壳与整体设计（`server.ts` / `public/` / 全局）

## ① 这段代码干什么

`src/server.ts` 用**原生 `node:http` + 手写路由表**起一个本地服务（默认 `http://127.0.0.1:8787`），
`public/` 下三个页面（知识体系 / 问答 / 学习计划与记录）用**原生 HTML + 原生 `fetch`** 直接调它。

**关键点：网页只是壳。** 它调的是和 CLI 演示**完全同一个内核**（同一个 `SimNet`、同一个 `QaEngine`、
同一个 `proposePlan`），没有为网页另写一套业务逻辑。

## ② 关键设计决策 + 为什么

| 决策 | 为什么这么定 |
|---|---|
| **用原生 `node:http` 手写路由表，不用 Express / Fastify** | 零依赖是硬约束（评审机要能直接跑起来）。本项目只有 9 条路由，手写一张 `if` 表完全够用，**且每条路由的行为都看得见**。 |
| **前端用原生 HTML + JS，不引 React / 不引构建** | 没有构建步骤 ⇒ 评审机**不需要 `npm install`** 就能看网页。题面也明确说"实现语言、技术栈、数据结构、接口风格均可自行选择"。 |
| **上传走 JSON（`POST /api/upload`），不做 `multipart/form-data`** | 省的是"表单解析"这一块代码，**上传功能本身是真的**：浏览器读到文件文本 → JSON 传 → 后端写盘 → **真抽取**（有 Key 走模型，见 Q4）→ integrate。 |
| **🔴 文件名白名单校验（拒 `\` `/` `..`）** | 上传接口直接写文件，**不做校验就是一个目录穿越漏洞**（`../../` 能写到 `data/` 外面）。前端能做校验，但**后端必须自己做**。 |
| **请求体限长 2 MB** | 防止一个超大请求把内存吃光。超限直接报错而不是截断。 |
| **绑定 `127.0.0.1`，不绑 `0.0.0.0`** | 这是本机演示用的服务，**没有鉴权**。绑 `0.0.0.0` 会把它暴露给整个局域网。 |
| **产物目录 = `data/.runtime/`，输入目录 = `data/`** | 见下面 Q2。 |
| **`GET /api/graph` 把 `cycles` 也返回了** | 让"环"这件事**在界面上可见**，而不是只躺在日志里。这也是"可解释"的一部分。 |
| **额外给了 `POST /api/propose`** | 把 §4.13 的"模型提议 → 校验 → 拒绝 → 回落"做成**可点、可看**的接口。拒绝理由、决策日志、回落后的计划一次返回。 |
| **首页用「分层 DAG 图」，不用树、不用力导向** | 见 Q11。一句话：树装不下多亲点、力导向不可复现，分层是 DAG 的标准画法且依据现成。 |

### 整体分层（如果被问"你怎么设计这个系统"）

```
                    ┌──────────────┐   ┌──────────────┐
   两个壳：          │  CLI 演示     │   │  网页壳       │
                    │  demo/*.ts    │   │  server.ts    │
                    └──────┬───────┘   └──────┬───────┘
                           └────────┬─────────┘
                                    ▼
              ┌────────────────────────────────────────┐
  业务内核：    │  SimNet（知识网络：integrate/计划/状态） │
              │  QaEngine（检索 + 充足性判定 + 上下文包） │
              │  proposePlan（模型提议校验/拒绝/回落）    │
              └───────────────┬────────────────────────┘
                              ▼
              ┌────────────────────────────────────────┐
  数据与基础设施：│ analyze/*（抽取：路B→路A→presets）      │
              │ normalize（归一化+别名）  store（原子写）  │
              │ llm（模型调用 + .env + 降级）             │
              └────────────────────────────────────────┘
```

**依赖方向是单向的**：壳 → 内核 → 数据层。反向没有任何 import（`network` 连 `plan` 都不直接依赖，
用回调注入）。所以：**换壳不用改内核**（网页和 CLI 共用），**换存储不用改业务**。

## ③ 可能被追问的问题

**Q1：网页和 CLI 会不会有两套逻辑、改一处忘另一处？**
> 不会。两者都只做两件事：**装配内核**（new SimNet / wireActions / new QaEngine）+ **调方法**。
> 所有业务规则（排序键、掌握度公式、充足性阈值）都只存在于 `src/` 里一份。

**Q2：为什么产物写在 `data/.runtime/`，而不是直接写 `data/`？**
> 因为我踩过坑：早期两个演示脚本都读写真实 `data/`，**跑第二次时状态已经被扣到 0**，
> 输出变成「掌握度 0.00 → 0.00」，而旁边的解说词还在说"做错后掌握度下降" —— **输出在反驳自己的解说词**。
> 而且 `full-demo`（模型抽出 26 个点）和 `l1-demo`（路 B 6 个点）会**互相污染同一份 `graph.json`**，
> 演示结果不可复现。
> 现在：**输入 `data/`（只读，且全部被 git 追踪）、产物 `data/.runtime/`（gitignore，每次演示前清空）**。
> 演示变成**幂等**的 —— 跑第 N 次和第 1 次输出一模一样（我用 `diff` 实测过）。

**Q3：`server.ts` 启动时会做什么？**
> ① 载入 `data/.runtime/` 里已有的 `graph.json` / `state.json`（**重启不丢状态**）；
> ② 把 `data/` 下所有资料 + 真题**按内容 hash 记账**后接入（幂等，见 Q10）；
> ③ 建检索索引。所以"重启服务 → 学习状态还在"本身就是一个持久化证据。

**Q4：上传之后发生了什么？**
> ① 写盘（`data/materials/xxx.md` 或 `data/problems/xxx.prob.md`）；
> ② **抽取**（这一步 2026-10-11 改过，是最容易被追问的点）：
> - 有 `DEEPSEEK_API_KEY` ⇒ 资料走 `net.analyzeRes()`（`analyzeResource` 的**路 A：模型逐块抽取 + schema 校验 + 失败重试一次**），
>   真题走 `net.analyzePro()`（让模型判断这题考哪些知识点）；模型不可用/抽不出 ⇒ 回落下一级；
> - 没 Key ⇒ 不调模型，按 **presets 预置 → md 声明**回落；
> - ③ `integrate`（知识点入图 / 边入 prev / 考频只在首入库 +1）→ 重建检索索引；
> - ④ 响应 `{ok, file, kind, extractedBy, points, edges, note}` —— **`extractedBy` 明确告诉你是"model / preset / rule"谁抽的**，
>   一份都抽不出时会带 `note` 说明原因（修掉了"上传成功但其实 0 个知识点"的静默失败）。
>
> ⚠️ 为什么真课件（PPT/教材转的 md）必须让模型抽：**它不会有 `## 知识点:` 声明**。
> 修之前 `/api/upload` 只走规则解析 ⇒ 这类资料上传后静默得到 0 个知识点，题面 L2 的"接模型解析"在网页上完全演不出来。
>
> 💡 顺带一个"边界"细节（可以主动讲）：`## 某某: 某某` 这种形式的**正文小标题也会被规则解析当成声明**
> （正则只认"`##` + 冒号"的形状）。所以规则路径只适合"我手写的、声明齐全的"资料；
> 真课件走模型，两者不冲突。

**Q5：为什么不做用户系统 / 数据库？**
> 题面没要求，且这是**单人本机学习工具**（题面场景是"学生自己上传资料"）。
> 引入账号 + 数据库会让"评审机跑起来"的成本暴涨，收益是零。
> 换成多人场景的话：`state` / `answers` 这些天然就是"按用户分表/分目录"的形状，扩展点是清楚的。

**Q6：那 `data/decisions.json` 和 `answers.json` 会越写越大吗？**
> 不会无限大：**保留最近 500 条**（按时间裁剪），README §8 有账本。

**Q7：你这套东西的可测性怎么保证？**
> 每条业务规则都有可断言的**数值结果**：掌握度 0.5 → 0.25、`pointRank(3)` 的顺序、
> `sufficient` 布尔值、拒绝理由数组、跨进程读回的掌握度。
> `tests/` 里 46 条用例覆盖 §8 验收清单（其中 6 条是**真起 server 子进程 + 真发 HTTP** 的网页壳端到端，含"模型调用失败时来源是否如实标注"），跑一条命令就能全验：
> `node --experimental-strip-types --test tests/*.test.ts`。

⚠️ **Q8：演示脚本里的"离线保底"真的完全不联网吗？**
> **是真的**，而且这是我特意加的：`QaEngine` 有一个 `offline: true` 档，`l1-demo` 用它。
> 原因：如果本机恰好配了 Key，"保底演示"就会偷偷走模型，**输出和我预期的、和别人机器上的都不一样**。
> 强制离线之后，`l1-demo` 的输出**与机器上有没有 Key 无关** —— 这才叫保底。

⚠️ **Q9：第 4 步"另起一个进程读回状态"，为什么不用同一个进程读内存？**
> 因为那**证明不了落盘**。同一个进程读内存里的 `Map`，无论有没有写文件都会"看起来还在"。
> 所以 `verify-persist.ts` 是**独立进程**（`execFileSync` 起子进程），它只能通过读磁盘拿到数据 ——
> 读到了，才说明真的写进去了。
> （注：本机审核环境禁止派生子进程时会报 `EBUSY`，这是环境限制不是代码问题；
> 手动单独跑 `demo/verify-persist.ts` 一样能验证。）

⚠️ **Q10：`serve` 每次重启都会重新接入 `data/` 里的资料吗？会不会越接越多？**
> **不会，这是我自己查出来并修掉的一个真 bug**（原注释写"已存在则幂等"，其实**不成立**）。
> 修前：每次启动都拿模型重抽 `data/materials/*.md`，而**模型抽出的点名是会漂移的**
> （同一份 m01 三次跑出 11 / 10 / 9 个点），新点名不断并进旧图 ⇒ 连着起三次服务，
> 知识点从 **21 → 27 → 40** 一路膨胀。
> 更麻烦的二次伤害：涨到 40+ 点时，网页的"让模型提议"会直接返 `by=none`
> （模型上下文过长、输出不再是合法 JSON）——**而那正是回答"AI 在哪决策"的那条路**。
>
> 修法（`src/ingest-ledger.ts`）：不再"看文件在不在"，而是**看内容变没变** ——
> 对每个文件算 **sha256**，写进 `data/.runtime/ingested.json` 这本"已接入记账"；
> 启动时逐个比对，**内容没变就整段跳过**（不调模型、不动图）。上传接口写完也**即时记账**。
> ⇒ 修后连起三次：**30 → 30 → 30**（实测），且模型提议恢复 `by=model`。
>
> 追一句"为什么用内容 hash 而不是文件路径 / mtime"：路径改了内容没改会被重复接，
> mtime 会被 `git checkout`、解压、复制整片刷新 ⇒ **只有内容哈希才真正等于"这份资料我抽过了"**。
> 也顺势保住了上传功能：**重启后上传的资料还在、且不会被重复抽**（原来那个"改成启动前清空"的方案
> 会把用户上传的内容一起清掉，所以没采用）。

⚠️ **Q11：首页为什么画成"分层图"，不用树状（思维导图）或者力导向？**
> 这是查过资料 + 拿真实数据验证过的决定，**三个候选各自的致命伤**：

| 候选 | 为什么不选（都拿本项目的真实数据说） |
|---|---|
| **树状 / 思维导图** | 树的定义是**每个节点只有一个上级**。但这份图里有 **3 个"多亲"点**：`整数加减` 有 **5 个前置**（数位对齐 / 加法逢十进一 / 减法借一当十 / 进位规则 / 退位规则），`小数加减`、`异分母分数相加减` 各有 2 个。还有 **7 个孤立点**（`移项` / `合并同类项` / `一元一次方程`…）**连父带子都没有**，树里根本没地方挂。硬画只有两条路：**复制节点**或**砍掉前置边** —— 两条都等于在图里撒谎。 |
| **力导向（force-directed）** | 它擅长表现"聚类"，**但看不出层级**（谁是前置、谁是基础一眼分不清）；更致命的是**同一份数据每次跑出来的位置都不一样**（力平衡是迭代出来的）⇒ **演示不可复现**，评委两次刷新看到两张不同的图，直接扣分。 |
| **分层（Sugiyama 思路）** ✅ | DAG 的标准画法。**分层依据是现成的**——就是 `makePlan` 用的**拓扑分层**；**层内顺序也是现成的**——就是计划排序键 `(已掌握?1:0, 掌握度, -考频, 名字)`。⇒ **确定性、可复现、一句话讲得清**（"层不是我摆的，是拓扑序算出来的"）。 |

> **另外两个刻意的决定**：
> ① **孤立点单独成列**（标题写"未关联知识点"）—— 不硬塞进图里假装它们有关系，这是"如实声明"；
> ② **不做树状大纲**——图和明细表已经覆盖了"结构"和"细节"两个视角，再加第三个视图只会**增加要解释的东西**，收益为负。
> （诚实补一句：层内顺序只按排序键排，**没做交叉最小化**（barycenter 那种），
> 所以少数边会有视觉交叉。换来的好处是**顺序与计划完全同源**、且可复现——这个取舍我认。）
